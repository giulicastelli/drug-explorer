Summary (from the two runs above)
  lock window = schema_and_truncate start -> commit step end (the loader's own clock): 16.190 s and 14.584 s;
    it is copy + index_build + build_drugs + analyze + commit (12.30 + 2.08 + 0.27 + 1.38 + 0.12 = 16.15 s; 11.30 + 1.53 + 0.34 +
    1.18 + 0.17 = 14.52 s, arithmetic), the same steps as the "about 13 s" estimated in round 2 from v2's means.
  reads outside the window: median 25.3 ms and 27.7 ms (max 34.5 and 38.2 ms).
  reads that waited: 1 per run (the probe is one reader, so the next ones queue behind it): 15.800 s and 14.332 s. Each started
    0.287 s and 0.103 s after the window opened and returned 0.103 s and 0.149 s before the loader saw its commit return: the
    server releases the lock at its commit, the client learns of it a little later. The reads started in the last 0.15 s of
    the window took 17-34 ms: they did not wait.
  every read returned 25 rows: a reader never sees the emptied table, it waits and then sees the new load (TRUNCATE takes
    ACCESS EXCLUSIVE, which conflicts with the ACCESS SHARE of a SELECT; the waiting read gets the committed rows).
  So: a page opened during a reload hangs for up to the whole window, 14.6-16.2 s here at 100%, then shows the new data.
  A reload happens only when someone runs the loader again (docker compose up, or run --rm loader); the app never reloads.

Judgement: not changed (right size). For one team's demo the loader runs at start, before the app exists
(service_completed_successfully), so no reader waits; only a reload by hand while the page is open does, and then for about
15 s, once. If it mattered (a dashboard that must stay up during reloads), a team would load into a new table instead:
CREATE TABLE labels_new, COPY, build its GIN index and the drugs rows, ANALYZE, and then in one short transaction
ALTER TABLE labels RENAME TO labels_old; ALTER TABLE labels_new RENAME TO labels; (the same for drugs); DROP TABLE labels_old.
Readers would then wait only for the renames, not for the COPY (prediction, not measured). The price: twice the table on
disk during the load, index and constraint names to manage, and more code in the loader.
